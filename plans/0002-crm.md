# STEWARD — CRM (0002)

Build the first real domain surfaces: manage **Clients** (branded orgs) and
their **Customers** (individuals/households). Introduces the pieces every later
plan reuses: STEWARD's own operable vocabulary and the FormBuilder.

## The vocabulary problem

GRAIN's `ActionName` is a fixed union (`demo.run`, `field.set`, …); STEWARD's
domain verbs aren't in it. Rather than fork GRAIN (that is plan 0006), STEWARD
runs its **own action registry** behind the **same** `POST /intent` door and the
**same** SSE hub. The door branches: GRAIN actions → GRAIN's interaction layer;
`steward.*` actions → STEWARD's dispatcher → services → RenderOps over SSE.
One door, one stream, two vocabularies.

STEWARD actions (this plan): `client.create`, `client.update`,
`customer.create`, `customer.update`, `customer.search`.

## FormBuilder

One schema-driven component with three modes:
- **create** — empty inputs, submit fires `*.create`.
- **edit** — inputs seeded from a record, submit fires `*.update`.
- **view** — display fields (no inputs); a toggle flips view↔edit in place.

AI-first: fields are operable — GRAIN's `field.set` can prefill a field for the
human to review (the AI never submits). Same surface authors and reads a record.

## Definition of done

- `steward.*` intents round-trip through `/intent` → services → audit → SSE.
- Create a Customer from the UI; it appends to the list over SSE.
- Toggle a Customer between view and edit; edit saves via `customer.update`.
- Client create with branding (colors, company info).
- Tests: dispatcher happy-path + validation; form render for each mode.
