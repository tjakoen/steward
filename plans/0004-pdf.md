# STEWARD — Branded ticket PDF (0004)

Milestone-1 closer: turn a ticket into a **branded PDF** the operator can hand
to a Customer. Pipeline is three hops, each a plain function:

```
Ticket + Customer + Client.branding
  → renderTicketDocument()   (self-contained branded HTML)
  → printToPdf()             (headless Chrome, CDP Page.printToPDF)
  → application/pdf bytes
```

Reuses the 0003 `Ticket` domain and `/tickets` surfaces unchanged. No new
domain types — `Branding` already exists on `Client` (0002): `logoDataUrl`,
`primaryColor`, `secondaryColor`, `companyInfo`, `pdfFooter`.

## Branding as CSS tokens (data, never hardcoded)

Resolve `ticket → customer → client → branding`, then emit branding as CSS
custom properties on the document root so the print stylesheet references
tokens, not literals:

```
:root {
  --brand-primary:   <primaryColor>;
  --brand-secondary: <secondaryColor>;
}
```

`logoDataUrl` inlines as `<img src="data:…">` (already a data URL — the PDF
stays a single self-contained file, no asset fetches). `companyInfo` prints in
the header block, `pdfFooter` in a fixed `@page` footer via a running element.
A Client with `logoDataUrl: null` degrades to a text wordmark; a blank color
falls back to a neutral default token. **No Client-specific strings in code.**

## Print document (`app/view/pdf.ts`)

`renderTicketDocument(ticket, customer, client): string` returns a **complete**
`<!doctype html>` — its own inline `<style>`, not the app chrome. This doc is
never served to the browser as a page; it is fed straight to Chrome. Structure:

- **Header**: logo (or wordmark) + `client.name`, `client.branding.companyInfo`.
- **Title block**: `ticketId`, `title`, Customer label (`personsLabel`), status,
  `dateInitiated` / `dateLastUpdated`.
- **Body**: `summary`, `nextAction`, `waitingOn`/`waitingSince` (only when set).
- **Progress log**: dated `progressLog` entries, newest first.
- **Comm refs**: `commRefs` table when present.
- `@page { size: A4; margin: … }` + `--brand-primary` accents on rules/headings.

All interpolation goes through the existing `esc()` — same escaping the app
views use. Pure function, no I/O → unit-testable without Chrome.

## CDP driver (`app/pdf/print.ts`)

`printToPdf(html: string): Promise<Uint8Array>`:

1. **Lazy browser**: on first call spawn headless Chrome
   `--headless=new --remote-debugging-port=0 --no-first-run --no-default-browser-check`,
   scrape the chosen port from stderr (`DevTools listening on ws://…`), keep the
   process for the server's lifetime (module singleton). Chrome path from
   `CHROME_PATH` env, default the macOS location
   `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`.
2. **Per request**: open a fresh CDP target (`Target.createTarget about:blank`),
   attach, `Page.enable`, set content via `Page.navigate` to a
   `data:text/html;base64,…` URL (avoids temp files), wait `Page.loadEventFired`,
   then `Page.printToPDF { printBackground: true, preferCSSPageSize: true }`.
   Response `data` is base64 → decode to `Uint8Array`. Close the target.
3. CDP transport = Bun's built-in `WebSocket`; requests are id-matched JSON. Thin
   helper, no puppeteer dependency (keeps the BREAD stack lean).
4. Graceful teardown: close the browser on `SIGINT`/`SIGTERM`.

Fallback noted, not built: if CDP proves flaky, `--print-to-pdf=<file>` one-shot
spawn per request is the escape hatch (slower, temp file).

## Route + surface

- `GET /tickets/:id/pdf` — resolve ticket→customer→client; 404 if the ticket is
  missing. `renderTicketDocument` → `printToPdf` → `new Response(bytes, {
  'Content-Type': 'application/pdf', 'Content-Disposition':
  'inline; filename="<ticketId>.pdf"' })`. Read-only (a render, not a mutation)
  → **no audit row, no /intent**; it stays a plain GET.
- Add a **Download PDF** link on `/tickets/:id` pointing at `…/pdf`.

## Definition of done

- `GET /tickets/:id/pdf` returns a valid `application/pdf` for a seeded ticket
  (verified: boot server, curl the route, `file` reports "PDF document").
- PDF shows the ticket's Client branding — logo, primary-color accents,
  companyInfo header, pdfFooter — sourced entirely from `Client.branding`.
- Two Clients with different branding produce visibly different PDFs from the
  same ticket shape (proves tokens, not hardcoding).
- `renderTicketDocument` unit tests: brand tokens present, footer text present,
  hostile input escaped, null-logo degrades to wordmark.
- CDP driver test emits a non-empty `%PDF`-prefixed buffer; **skips** cleanly
  when no Chrome binary is resolvable (CI-safe).
- `bun run check` clean; `bun test` green; end-to-end verified.
